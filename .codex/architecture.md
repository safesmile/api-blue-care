# Reglas permanentes de Blue Dent

- API exclusiva de Blue Dent: monolito modular NestJS, sin multitenencia, organizaciones ni librería externa Kraken.
- PostgreSQL y Sequelize 6 con sequelize-typescript. Nunca MongoDB. Cambios de esquema mediante migraciones versionadas; synchronize siempre false.
- DDD pragmático: módulos por contexto de negocio con domain, application, infrastructure y presentation. Domain no importa Nest, Sequelize, HTTP ni DTOs. Application coordina reglas y puertos del dominio, nunca modelos Sequelize ni DTOs HTTP. Se permite DI de Nest en application para mantener sencillez.
- Infraestructura implementa repositorios, hash, correo y acceso externo. Modelos SQL no son entidades. Presentation contiene controladores, DTOs con validación, decoradores y permisos.
- Repositorios y casos de uso heredan contratos abstractos CRUD con create, read, list, update y delete cuando corresponde. Controladores heredan contratos sin decoradores. Implementar cada método y endpoint explícitamente; no fábricas que expongan CRUD automáticamente.
- No crear abstracciones sin necesidad, controladores con lógica de negocio, dependencias circulares ni carpetas compartidas que acumulen reglas de pacientes o citas.
- Identificadores UUID. Paginación limitada, filtros y campos de orden explícitamente permitidos al añadirlos; nunca trasladar consultas SQL arbitrarias del cliente.
- JWT HS256 con issuer/audience y expiración corta, sesión persistida y revocación comprobada en cada petición. Refresh aleatorio, hash SHA-256, rotación transaccional con bloqueo de fila y límite absoluto de sesión. Logout revoca la sesión. La rotación invalida también el JWT anterior: el cliente debe sustituir ambos tokens de forma coordinada.
- Contraseñas bcrypt coste 12, mínimo 8 caracteres, mayúscula/minúscula/número/símbolo, máximo 72 bytes UTF-8. No devolver hashes ni registrar contraseñas o tokens. Permisos tipados; denegar por defecto salvo @Public explícito.
- Alta operativa: npm run createSuperUser solicita nombre, apellido, email y contraseña oculta con confirmación; sincroniza permisos y roles y crea una cuenta verificada con superadmin. No exige users vacía y nunca sobrescribe emails existentes. admin:create es alias del mismo asistente. Altas ordinarias por administrador o invitación. No hay registro público. Invitación verifica control del correo. No habilitar multitenencia ni registro abierto sin petición del usuario.
- Google Cloud con Application Default Credentials y cuenta de servicio adjunta en producción. Nunca copiar credenciales de los proyectos del trabajo. Archivos clínicos privados; persistir claves de objeto y generar enlaces firmados cortos después de autorizar acceso al recurso clínico.
- Toda integración nueva debe tener puerto, adaptador y configuración explícita. Correo SMTP; no emitir correos reales en pruebas. Si se requieren notificaciones o chains, primero definir el caso de negocio; procesos durables deben persistir su estado y ser idempotentes. No ejecutar tareas durables en memoria.
- .env no se versiona; .env.example sin secretos. Secret Manager opcional antes de iniciar Nest. Variables explícitas del proceso prevalecen sobre el JSON del secreto.
- Los proyectos kraken-nest y backend-synctasks son referencias de lectura, no destinos de cambios ni dependencias de esta API.
- Verificar build, lint, pruebas unitarias y test:integration al cambiar autenticación o persistencia. Integración usa PostgreSQL desechable Docker, nunca bases configuradas por el usuario.

- Formato y pruebas: cumplir .codex/testing.md. Cada caso de uso y controlador requiere su spec separado bajo src/test/modules/<modulo>; no agregar specs junto a producción. ESLint y Prettier deben concordar y pasar sin errores ni advertencias.

- TypeScript: mantener strictPropertyInitialization activo. En DTOs, las propiedades obligatorias hidratadas por Nest/class-transformer usan asignación definitiva (!), las opcionales usan ?, y los valores por defecto solo se agregan cuando tienen significado funcional. Los atributos gestionados por Sequelize usan declare. Las propiedades del dominio se inicializan mediante constructor. No desactivar la comprobación para ocultar errores.

- Autorización relacional: Cada módulo posee su archivo de dominio *.permissions.ts con sus códigos y definiciones. src/permissions.ts contiene exclusivamente las políticas DEFAULT_ROLE_PERMISSIONS y nombres de roles; no agrega catálogos ni operaciones. La infraestructura permission-registry registra los catálogos de módulos para la sincronización, y auth.throttle.ts define los límites públicos. Roles superadmin/admin/customer protegidos; superadmin obtiene todo el catálogo, admin y customer disponen de perfil y cambios de credenciales propios; los permisos administrativos de negocio quedan por definir. No hay permisos directos editables en usuarios; los grants provienen de roles y se resuelven en cada petición. Roles se asignan por nombre en los DTOs y exigen roles:assign; otorgar o modificar superadmin requiere ser superadmin. Cada operación privada debe declarar su permiso explícito; si falta, se deniega. Operaciones públicas usan @Public y @Throttle. Sin catálogo en línea por ahora.
- npm run permissions sincroniza tablas y roles por transacción, conserva IDs y membresías, elimina permisos retirados y sobrescribe grants de roles predeterminados desde el catálogo. No promueve usuarios: el argumento --superadmin-email fue retirado. La migración roles-permissions solo crea tablas, claves e índices; la inserción/actualización de roles y permisos pertenece al script. Los permisos históricos se convierten una vez durante sincronización, sin perder accesos ni conceder superadmin automáticamente. Nuevas entidades/tablas requieren migraciones; nunca ejecutar sincronizaciones contra la base del usuario como parte de pruebas.

- Identidad: almacenar firstName, lastName y verified además de name por compatibilidad. La cuenta creada por createSuperUser es enabled=true y verified=true. Login, refresh y guard rechazan cuentas no verificadas. Nunca registrar contraseñas; las entradas interactivas usan salida silenciada y confirmación. No crear una cuarta variante de rol superuser: el superusuario usa el rol canónico superadmin.

- Convención de archivos aclarada por el usuario: conservar los sufijos .controller, .module, .dto, .inputs, .middleware y .permissions. Para los casos de uso, usar .usecase, nunca .use-case. No concatenar el sufijo con el nombre ni renombrar tablas, constantes o módulos por esta convención.

- No persistir permisos efectivos en users: se resuelven desde user_roles, roles, role_permissions y permissions. UserProps.permissions y la respuesta JSON son proyecciones calculadas, no columnas. La migración 005 elimina las columnas legacy solo si ya no contienen grants; para instalaciones existentes ejecutar permissions antes de db:migrate. Las modificaciones de roles deben persistir user_roles en la misma transacción que el usuario y devolver permisos recalculados.

- Seeders explícitos de prueba: db:seed sincroniza permisos y crea un usuario verificado/habilitado por rol predeterminado, con la contraseña fija solicitada por el dueño (Pa$$word123), almacenada con bcrypt coste 12 y sales independientes. Es una excepción exclusiva para fixtures de prueba; no crear estas cuentas al arrancar la API. db:migrate:reset encadena undo:all, migraciones y db:seed. El seeder debe ser repetible, proteger cuentas ajenas con emails/IDs coincidentes y asignar roles en user_roles.

- M01: aplicar .codex/m01-authentication.md. Customer representa por ahora al paciente, sin membresía comercial automática. Nuevos usuarios HTTP quedan verified=false y solo se activan por token al contacto registrado. Invitaciones tienen entidad/historial propio; conservar estados y fechas al aceptar/revocar, rotar tokens al reenviar y registrar el resultado SMTP. En clientes customer, además del permiso comprobar propiedad del ID de identidad; el futuro módulo de pacientes deberá extender esa política a todos sus recursos clínicos. Cambios de email requieren prueba del canal nuevo antes de cambiar o vincular contacto.
